Dettagli pratici per integrazione (richiami, formato risposta, errori)

- MangaDex (Manga)
    - Base URL: https://api.mangadex.org
    - Come chiamare: GET /manga?title=<term>&includes[]=author&includes[]=artist&includes[]=cover_art
        Esempio: https://api.mangadex.org/manga?title=one%20piece&includes[]=author&includes[]=artist&includes[]=cover_art
    - Forma risposta: JSON con `data` (array di risorse), `pagination`, `attributes` e `relationships`.
        Esempio ridotto: {"data":[{"id":"...","attributes":{"title":{"en":"..."}}}],"pagination":{"total":5}}
    - Feed capitoli: GET /manga/{id}/feed?translatedLanguage[]=it&translatedLanguage[]=en&order[chapter]=asc
    - Lettura pagine: GET /at-home/server/{chapterId}
    - Cover: https://uploads.mangadex.org/covers/:manga-id/:cover-filename.512.jpg
    - Errori comuni: 400 Bad Request, 404 Not Found, 429 Too Many Requests, 500 Server Error.
    - Note: API pubblica e gratuita; credit obbligatorio a MangaDex e ai gruppi scanlation; niente ads o servizi a pagamento.

- Open Library (Books metadata)
    - Base URL: https://openlibrary.org
    - Come chiamare: GET /search.json?q=<term>
        Esempio: https://openlibrary.org/search.json?q=harry+potter
    - Forma risposta: JSON con `numFound` e `docs` (array). Ogni doc contiene title, author_name, isbn, edition_key, ecc.
        Esempio: {"numFound":123,"docs":[{"title":"...","author_name":["..."],"isbn":["..."]}, ...]}
    - Errori comuni: 429 Rate Limit, 500 Server Error.
    - Note: non richiede chiave; usare `User-Agent` con email per limiti migliori. Default ~1 req/sec, 3 rps se identificati.

- Google Books
    - Base URL: https://www.googleapis.com/books/v1
    - Come chiamare: GET /volumes?q=<term>&key=<API_KEY>
        Esempio: https://www.googleapis.com/books/v1/volumes?q=tolkien&key=YOUR_KEY
    - Forma risposta: JSON con `kind`, `totalItems`, `items`[]. Ogni item contiene `id` e `volumeInfo` (title, authors, imageLinks, accessInfo...)
        Esempio: {"kind":"books#volumes","totalItems":2,"items":[{"id":"...","volumeInfo":{"title":"..."}}]}
    - Errori comuni: 400/401/403 (API key mancante o non valida), 429 Quota exceeded, 500 Server Error.
    - Note: richiede API key per produzione; utile per cover/previews/accessInfo.

- Gutendex (Project Gutenberg metadata)
    - Base URL: https://gutendex.com/books
    - Come chiamare: GET /books?search=<term>&page=<n>
        Esempio: https://gutendex.com/books?search=frankenstein
    - Forma risposta: {"count":<n>,"next":"...","previous":null,"results":[{id,title,authors,formats,...}]}
    - Errori comuni: 404 (id non trovato), 500.
    - Note: ottimo per public-domain texts; nessuna auth; per carico elevato meglio self-hostare.

- The Guardian Open Platform (News)
    - Base URL: https://content.guardianapis.com
    - Come chiamare: GET /search?q=<term>&api-key=<KEY>&show-fields=thumbnail,trailText,body
        Esempio: https://content.guardianapis.com/search?q=climate&api-key=YOUR_KEY&show-fields=trailText,thumbnail
    - Forma risposta: {"response":{"status":"ok","results":[{"id":"...","webTitle":"...","webUrl":"...","fields":{...}}]}}
    - Errori comuni: 401/403 (chiave), 429 (quota giornaliera), 500.
    - Note: richiede registrazione per ottenere API key; quota tipica per developer ≈500 req/day (richiedere aumento se necessario).

- GDELT (analytics/news dataset)
    - Tipologia: dataset + API di sintesi; uso tipico via BigQuery o download dei dump.
    - Per UI: preferibile usare Summary APIs o un proprio pipeline; non è pensato per fetch di singoli articoli.
    - Errori/attenzioni: dataset molto grande, latenza e complessità di query; non adatto come unica sorgente per articoli completi.

Consigli integrazione (pratici):
- Implementare un proxy server-side (Nuxt server routes) che normalizzi risposte e mantenga le chiavi API.
- Cache preferita: Redis. TTL suggeriti: search = 1h, dettaglio risorsa = 24h, news = 30m.
- Rate-limiter upstream (es. Bottleneck): reservoir 60/min, minTime ~334ms; gestire 429 con backoff/escalation.
- Usare ETag / If-None-Match per evitare traffico inutile; servire 304 Not Modified quando possibile.
- Tradurre errori upstream in payload client-friendly (es. mettere header X-Upstream-Status, Retry-After).

Obiettivo della pagina:
- click su un item della carousel -> route dinamica `/${tipo}/${id}`

STRUTTURA API E PAGINA

1. LIBRI

API preferite: Open Library, Google Books, Gutendex.

Open Library
- Request: `GET /search.json?q=<term>` oppure `GET /works/<key>.json`
- Input principale: testo di ricerca, `key` dell'opera, eventuale pagina
- Response: `numFound`, `docs[]` o record singolo con titolo, autori, ISBN, copertina, soggetto, anno
- Uso nel sito: ricerca catalogo, metadati, copertine, link alla scheda libro
- Pagina dettaglio: hero con copertina, autore, anno, generi, sinossi, pulsanti salva/acquista/leggi, sezione libri simili

Google Books
- Request: `GET /volumes?q=<term>&key=<API_KEY>` oppure `GET /volumes/<id>`
- Input principale: query di ricerca, id volume, filtri facoltativi
- Response: `totalItems`, `items[]`, `volumeInfo`, `accessInfo`, `imageLinks`
- Uso nel sito: catalogo ricco, preview, copertine, stato di accesso al volume
- Pagina dettaglio: blocco preview, metadati completi, badge `preview`, pulsante apri anteprima, commenti, salvataggio

Gutendex
- Request: `GET /books?search=<term>&page=<n>` oppure `GET /books/<id>`
- Input principale: termine di ricerca, pagina, id libro
- Response: `count`, `next`, `previous`, `results[]`, con titolo, autori, formati, testo in pubblico dominio
- Uso nel sito: libri gratuiti e leggibili integralmente
- Pagina dettaglio: evidenza del testo completo, pulsante leggi ora, formati disponibili, download, capitoli o sezioni

Server route suggerita per i libri
- `/api/books/index.get.ts`: ricerca e lista catalogo
- `/api/books/[id].get.ts`: dettaglio singolo libro
- `/api/books/[id]/comments.post.ts`: nuovo commento

2. MANGA

API consigliata: MangaDex.
I manga sono divisi in capitoli, quindi la pagina principale è il Manga con la lista dei capitoli; il reader può aprire il capitolo interno oppure rimandare alla fonte esterna.

MangaDex
- Request: `GET /manga?title=<term>&limit=<n>` oppure `GET /manga/<id>`
- Input principale: titolo, filtri, pagina, id MangaDex
- Response: `data[]`, `pagination`, `relationships`, con titolo, copertina, synopsis, generi, autori, stato e ultimo capitolo
- Feed capitoli: `GET /manga/<id>/feed?translatedLanguage[]=it&translatedLanguage[]=en&order[chapter]=asc`
- Input principale feed: lingua, ordine capitoli, paginazione
- Response feed: `data[]` con `chapter`, `volume`, `translatedLanguage`, `publishAt`, `pages`
- Download pagine: `GET /at-home/server/<chapterId>` per ottenere baseUrl, hash e immagini
- Uso nel sito: fonte principale per schede manga, capitoli, lettura e reader
- Pagina dettaglio: copertina, metadati, capitoli, lingua, lettura progressiva, link al reader

Server route suggerita per i manga
- `/api/manga/index.get.ts`: ricerca e lista catalogo
- `/api/manga/[id].get.ts`: dettaglio singolo manga
- `/api/manga/[id]/comments.post.ts`: nuovo commento

Fonte prevista: database interno o API esterna da decidere in base alla disponibilità.

Request

- Se esterno: stessa logica di proxy e normalizzazione del resto del progetto

Response
- array con `title`, `coverUrl`, `chapters`, `language`, `description`, `status`, `type`

Uso nel sito
- catalogo a griglia con copertine
- pagina dettaglio orientata alla lettura di immagini o capitoli

Pagina dettaglio comics
- cover e titolo in alto
- lettore immagini o capitoli sequenziali
- box info con autore, genere, stato, numero tavole
- azioni: salva, compra, commenta, continua la lettura

Server route suggerita per i comics
- `/api/comics/index.get.ts`
- `/api/comics/[id].get.ts`
- `/api/comics/[id]/comments.post.ts`

4. GIORNALI E NEWS

API possibili: The Guardian Open Platform, GDELT.

The Guardian Open Platform
- Request: `GET /search?q=<term>&api-key=<KEY>&show-fields=thumbnail,trailText,body`
- Input principale: parola chiave, sezione, data, paginazione
- Response: `response.status`, `response.results[]`, con titolo, URL, estratto, immagine, corpo articolo
- Uso nel sito: news leggibili, ricerca per argomento, articoli completi dove permesso
- Pagina dettaglio: titolo, fonte, data, immagine, sommario, corpo articolo, link originale, salvataggio

GDELT
- Request: query su endpoint di sintesi o pipeline interna, non come singolo articolo classico
- Input principale: argomento, lingua, finestra temporale, area geografica
- Response: dataset aggregato, eventi, articoli correlati, trend e fonte
- Uso nel sito: sezione giornali più orientata a raccolta e trend che a lettura articolo per articolo
- Pagina dettaglio: riepilogo, correlazioni, articoli collegati, fonte di provenienza

Server route suggerita per i giornali
- `/api/news/index.get.ts`
- `/api/news/[id].get.ts`
- `/api/news/[id]/comments.post.ts`

STRUTTURA UI DELLA PAGINA DETTAGLIO

Sezioni comuni:
- header con breadcrumb e categoria
- hero con cover/immagine principale
- colonna sinistra con preview o lettore
- colonna destra con metadata e azioni
- tab o sezioni per descrizione, capitoli, commenti, correlati

Comportamento responsive:
- desktop: layout a due colonne
- mobile: hero in alto, azioni sotto, lettore a tutta larghezza
- la carousel deve sempre rimandare alla pagina dettaglio dello stesso tipo di contenuto

Componenti utili:
- `ObjectHeader.vue`: titolo, autore, badge, rating
- `ObjectActions.vue`: salva, acquista, leggi, condividi
- `ObjectMetadata.vue`: anno, genere, lingua, stato, source
- `ObjectReader.vue`: area lettura o preview
- `RelatedItems.vue`: contenuti simili
- `CommentsPanel.vue`: commenti live via Socket.IO

Regola di progetto:
- tutte le API esterne vengono passate da server routes Nuxt
- la pagina non parla mai direttamente con l'API esterna
- ogni risposta viene normalizzata nello stesso formato, così la UI resta uguale per libri, manga, comics e news

Inserimento oggetti da API nel database, Like, commenti, liste...
Quando un utente apre la pagina di un oggetto, che sia Libro, Manga o News, questa viene inserita nel database coem catalog_items, source sarà ovviamente API ed external_provider da quale API viene presa ed external_id l'ID dell'oggetto dall'API. grazie a questo, i like e commenti (saranno tutti interni al sito) possono essere messi sia agli oggetti presi dalle API che a quelli interni al sito. 

FLUSSO APPLICATIVO (OGGETTI API + LIKE/COMMENTI)

1) Apertura pagina oggetto
- Input pagina: type + external_id (se arriva da API esterna) oppure item_id interno.
- Server route:
    a) Se source=api: fetch API esterna.
    b) Normalizza risposta nel formato comune.
    c) Upsert catalog_items (chiave unica: type + source + external_provider + external_id).
    d) Upsert catalog_item_translations per lingua (title/description).
    e) Upsert item_media per cover/immagini.
    f) views_count = views_count + 1.
    g) Carica stato utente: isLiked, isSaved, isPurchased, canLike, canComment.
    h) Risposta: item_id interno + oggetto normalizzato + flags.

2) Like (toggle)
- UI click sul cuore.
- Se non loggato: login modal o redirect.
- Backend: insert/delete su item_likes.
- Se like = true: aggiunge anche in lista "Preferiti" (user_list_items).
- Risposta: liked, likesCount, saved.

3) Commenti
- UI invio commento.
- Backend: validazione + sanitizzazione input.
- Permessi: canComment se reading_progress.percentage >= soglia (default 10%, configurabile).
- Inserimento in comments.
- Se Socket.IO attivo: broadcast nuovo commento alla pagina.

UI LIKE
- Bottone cuore con stato: off (contorno) / on (pieno).
- Tooltip: "Aggiungi ai preferiti" / "Rimuovi dai preferiti".
- Contatore like vicino al bottone.
- Stato loading durante la request, update ottimistico con rollback su errore.
